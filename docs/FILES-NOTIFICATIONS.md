# 文件传输与桌面通知

## 文件管理器

展开 Webtop 工具栏 → **文件 → 下载文件**，会打开内置文件管理器。默认根目录是 `/config/projects`，可进入子文件夹或新建文件夹，再点 **上传** 选择本机文件；每项旁边的下载按钮可取回文件。工具栏直接的“上传文件”入口适合上传到根目录，选择目标子目录时使用文件管理器里的“上传”。

文件走浏览器当前的 HTTPS 管理连接，直接写入容器可见的目录，不需要先 SSH 上传到宿主再手动复制。Docker 持久卷仍实际存储在宿主 `webtop-data/projects`，网络和存储没有绕过承载容器的宿主机。通过 Tailscale 入口可以不依赖 Mac 的 localhost SSH 转发。

`.env` 的 `FILE_MANAGER_PATH` 可改为 `/config` 下的其他目录；默认 `/config/projects`。干净部署由 `prepare.py` 创建该目录。已有 HOME 不要重新运行种子覆盖；应手动创建需要的目录并核对 UID/GID。

文件管理器展示的“文件”根就是该配置目录，不展示 `/config/.ssh` 等兄弟目录。这是操作范围设置，不是同一个桌面用户之下的额外安全隔离。

## 浏览器通知

通过可信 HTTPS 打开 Webtop，展开左侧 Selkies 工具栏，在底部点击 **🔔 开启桌面通知**，允许当前站点通知；按钮显示“桌面通知已开启”时链路就绪。收起工具栏也会收起按钮，通知连接继续保留，按钮不再覆盖远程应用的错误提示或输入区。当前浏览器已允许的站点会沿用权限。换用 localhost 或另一节点域名，需要分别开启。Mac 系统通知设置、专注模式以及浏览器权限仍决定最终是否弹出。

页面保持连接时，桌面会话发往 `org.freedesktop.Notifications.Notify` 的通知会转为本机浏览器通知，切到其他标签页或应用仍可接收。应用本身必须发出 Linux 桌面通知；没有把 Claude 会话内容或任务完成状态另行推断为通知。点击通知会尝试聚焦 Webtop。

开启通知后，页面会把窗口 focus/blur 和可见状态经同一个认证通道同步到桌面。Mac 切走时暂时清除远端 X11 输入焦点，避免 Claude 仍把自己当作前台应用而抑制通知；切回来时仅在焦点尚未被别的控制端改变、原窗口仍存在的情况下恢复。多个有订阅的控制端中任一仍在前台时，保持桌面前台状态；关闭页面会释放其状态，失联状态有超时。窗口 ID、通知正文不会被记录到此状态接口。

macOS 的通知设置可能列出两个“Google Chrome”，其中一个是通知辅助组件。检查对应项的 Allow notifications、Desktop 和 Notification Center；如果短暂横幅容易错过，可将实际发布通知的 Chrome 主项设为 Persistent（持续提醒）；只给网站授权不足以覆盖系统层禁用。不要为此关闭 TLS、开放额外端口，或自动更改全局专注/屏幕共享隐私设置。

关闭页面、浏览器休眠/丢弃标签页或连接断开期间不保证收到；没有 Web Push、离线补发、通知历史或第三方推送服务。再次点击按钮可关闭转发，选择保存在当前浏览器站点存储里。

## 启动与权限

- i3 普通 `exec` 启动用户级 DBus 监听器，单实例锁防止重复；保留原桌面通知守护进程。
- root 初始化脚本从只读 `desktop/notifications` 挂载安装小型 Selkies hook；转发后端随 Selkies 以桌面用户运行。没有新增 TCP 端口、容器能力或 Docker socket。
- 通知及焦点指令 Unix socket 均位于用户私有状态目录，权限 0600。正文只在内存中传送，不写历史或正文日志；包大小、客户端队列和发送频率有上限。
- HTTP 状态与 SSE 路由使用现有 Selkies 认证中间件，拒绝 viewer 和跨站请求；该机制不增加 Webtop 本来没有的用户登录系统。管理入口仍依赖既有 SSH/tailnet 访问控制。

`install.py` 只接受固定镜像的原始 `stream_server.py` SHA-256：`82cf2855de173bd8e7e3e90f544c1486a0c327771c1d275998e212ff7a7738cb`。重复执行幂等；来源不匹配时跳过通知补丁。通知接收器启动失败会禁用此功能，不阻止桌面 HTTP 服务启动。升级镜像必须重新比较源码和事件循环兼容性。

已有安装需备份并合并 Compose 的 `FILE_MANAGER_PATH`、两项只读挂载、HTML 中的通知脚本、用户监听器及 i3 启动项。现有运行容器可在授权维护时原地安装，随后仅重启 Selkies 并刷新页面；完整重建应安排维护窗口，会结束应用。不要把旧运行 HOME 覆盖为仓库种子。

## 已验证范围

2026-11-13 源机：Mac 通过 Tailscale HTTPS 调用同一个上传 API，将 125 B 合成文件写入 UI 创建的子目录；刷新后的文件管理器可见，浏览器下载后 SHA-256 与原文件一致。自动化文件选择器因 Chrome 扩展未启用本地 file URL 访问而未完成，未扩大扩展权限；正常手动选择文件不依赖该自动化权限。

两条合成 Linux 桌面通知由浏览器收到并触发 `Notification.onshow`。测试中曾切换本地标签页，但浏览器工具返回的文档可见性仍为 `visible`，因此没有把 hidden 状态当成独立验收通过项；也没有触发真实 Claude 任务来验证其具体通知行为。

使用镜像自带 aiohttp 与 uvloop 的隔离测试验证 401/403、SSE、socket 清理及故障隔离；部署时 Chrome、Claude、i3 进程保留。尚未进行这批新增配置的完整宿主重启或全新容器重放。机器可读记录见 [验证结果](../validation/files-notifications.json)。

## Claude Capabilities 页面变灰

如果点击后只有左侧选中项改变、右侧仍显示旧页且发灰，先用 Claude 应用 View → Reload（F5）重新加载嵌入网页，再重新进入设置。2026-11-13 的源机这样恢复了 Capabilities 内容；未清除 Cookie、未重装应用，也没有强行打开账号功能。诊断时所需静态模块通过同一代理可以正常获取，旧页面的异步加载状态卡住；不能据此将任意灰色功能都认定为同一原因。

焦点同步新增验证：19 项 Python 测试、3 项 JS 事件状态测试通过；在独立临时 Xvfb 显示中确认真实 X11 清焦点与恢复成功，个人桌面显示未用于此隔离测试；uvloop HTTP 测试覆盖未订阅、viewer、跨站及畸形请求拒绝。用户手动切到 Mac 其他应用/标签页后，已从后台独立确认 `desktop_active=false`、X11 输入焦点为 `0`，且监听器和订阅保持在线。后台合成通知已被桥接接收，用户确认通知中心收到。Chrome 主通知项从 Temporary 改为 Persistent 后，用户确认右上角持续提醒出现；切回 Webtop 后已确认恢复原应用输入焦点。真实 Claude 任务完成通知未另行触发验证。见 [状态记录](../validation/notification-attention.json)。
